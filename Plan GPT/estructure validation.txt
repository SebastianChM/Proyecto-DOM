Plan Mejorado de Implementación: Motor de Cumplimiento y Verificación BIM

El objetivo es desarrollar un sistema robusto para auditar automáticamente modelos BIM (Revit) contra especificaciones técnicas de proyecto (ET) y normativas regulatorias, detectando elementos del modelo que no cumplen requisitos. A continuación se detalla el flujo de usuario esperado, la gestión de documentos, la extracción de reglas, detección de conflictos, precisión requerida, visualización 3D de incidencias, generación de resultados, y cómo integrar todo con la arquitectura existente de la plataforma.

Flujo de Usuario Esperado

Carga de Archivos: El usuario sube a la aplicación web los documentos necesarios:

Modelo BIM (Revit): Un archivo .rvt del proyecto. (En la implementación actual ya se soporta la carga y traducción a formato APS para visualizar y extraer propiedades.)

Especificación Técnica (ET): Un documento PDF con todos los requerimientos técnicos del proyecto (obligatorio para esta funcionalidad).

Normativa de Referencia: Opcionalmente, otro PDF con normas de construcción aplicables (código de edificación, normas nacionales, etc.).

Configuración de Análisis: El usuario puede elegir qué especialidad o categoría desea verificar (por ejemplo: arquitectura, estructura, HVAC, electricidad, iluminación, o “todas” para una verificación completa). Esto filtra o prioriza las reglas a revisar según la especialidad seleccionada.

Inicio del Análisis: El usuario pulsa el botón “Analyze Document” (Analizar Documentos). En este punto se lanza el proceso de verificación:

En segundo plano, el backend procesa los PDFs para extraer las reglas y requisitos de la ET (y de la normativa si se proporcionó) y prepara los datos del modelo BIM para la comparación.

Se mostrará al usuario algún indicador de progreso, ya que el análisis es complejo y puede tomar varios minutos (5-10 min es aceptable según lo previsto).

Visualización de Resultados: Una vez completado el análisis, la interfaz muestra una pantalla dividida:

En una mitad, el visor 3D del modelo Revit (basado en Autodesk Viewer) mostrando el modelo;

En la otra mitad, una vista del documento PDF (ET o normativa).

Aparece además un panel lateral de incidencias listando los requerimientos verificados. Cada incidencia indica qué parte no se cumple, con un resumen del requisito y elemento(s) afectado(s).

Exploración de Incidencias: El usuario puede interactuar con las incidencias:

Al seleccionar una incidencia en la lista, la vista 3D resalta en rojo los elementos del modelo involucrados (por ejemplo, muros que no cumplen cierta resistencia al fuego) y acerca/zoomea a ellos en el modelo para inspección detallada. Esto es similar a cómo la herramienta Autodesk Model Checker permite “hacer zoom y seleccionar elementos no conformes directamente desde los resultados”
interoperability.autodesk.com
.

Simultáneamente, en la vista PDF, se desplaza o resalta la sección/párrafo relevante del documento donde está el requisito incumplido, marcado en rojo. De este modo el usuario ve en paralelo qué exige el documento y qué parte del modelo no lo cumple.

El usuario puede navegar libremente por el modelo 3D (rotar, hacer zoom, aislar elementos) y por el PDF, pero la sincronización facilita ubicar rápidamente cada problema.

Notificaciones/Resumen: El sistema registra las incidencias encontradas (vinculadas al proyecto/modelo y al documento PDF analizado). En la interfaz principal de la aplicación, el usuario podría ver un resumen o notificación indicando que el modelo analizado tiene X incumplimientos. Así, el equipo de arquitectura/ingeniería puede revisar todos los errores detectados y trabajar en corregirlos.

Gestión de Documentos de Especificaciones y Normativas

Cantidad de Documentos: Por cada análisis de un proyecto se espera al menos un documento de Especificación Técnica (ET). Este es el documento definitorio principal contra el cual se valida el modelo (obligatorio). Adicionalmente se puede permitir un documento de Normativa aplicable (opcional). En esta primera implementación, limitar a uno de cada tipo simplifica el flujo y la comparación (evita manejar múltiples PDFs de cada tipo).

Recomendación: Mantener un PDF de ET por proyecto garantiza claridad sobre cuáles son los requerimientos a cumplir. Si en el futuro surgiera la necesidad de múltiples ET (ej. distintas disciplinas separadas), podría ampliarse, pero inicialmente una ET central es lo óptimo. Para normativas, también se recomienda un documento compilado con las secciones normativas relevantes, para no cargar demasiados PDFs; sin embargo, se podría ampliar a varios documentos normativos si fuese necesario, fusionando sus requisitos en el análisis.

Subida y Asociación: En la UI, probablemente el usuario seleccione o suba estos PDFs en secciones designadas:

Un campo para ET (PDF) – requerido (por ejemplo, “EspecificacionesTecnicas.pdf”).

Un campo para Normativa (PDF) – opcional (por ejemplo, “NormativaSismo.pdf”).

Estos podrían almacenarse en el servidor o base de datos asociados al proyecto/modelo para uso durante el análisis.

Actualización: Si se sube una ET nueva o se actualiza, habría que reanalizar el modelo para recalcular el cumplimiento según la nueva versión. Similar con la normativa. (Esto implica invalidar o recalcular las incidencias previas para ese proyecto).

Separación Lógica: Internamente, trataremos las reglas de la ET y las reglas de la Normativa por separado primero, ya que su origen y prioridad difieren:

Reglas de ET: Requisitos específicos del proyecto (por encargo del cliente o diseño) que el modelo debe cumplir primordialmente.

Reglas de Normativa: Exigencias legales o de estándares generales. Se considerarán un “plus” en el sentido de que el proyecto debe cumplirlas para estar conforme a código, aunque quizás la ET no las enumere todas. Servirán para detectar situaciones donde “cumple la ET pero no la normativa”, que igualmente son relevantes.

Especialidad/Categoría: Dado que la ET puede contener secciones por disciplina (ej. capítulo de arquitectura, capítulo eléctrico, etc.), se aprovechará esa estructura para etiquetar las reglas por especialidad. De igual modo, las normativas suelen estar organizadas por tema (ej. seguridad contra incendios, estructural, eficiencia energética). Al cargar los documentos, el usuario puede marcar todas o filtrar especialidades; esto posiblemente simplemente filtre la visualización de incidencias luego. Por ejemplo, podría haber un checkbox para cada disciplina, para mostrar/ocultar las incidencias correspondientes a esa disciplina. De todos modos, el análisis completo se realiza sobre todas las reglas, pero la UI permite focalizarse en lo deseado.

Estructura y Extracción de Reglas de los Documentos (ET y Normativa)

Dado que las especificaciones y normativas vienen en PDF (no estructurados para máquina), es crucial extraer el contenido con su estructura jerárquica y semántica. Esto permitirá entender el contexto de cada requisito (por ejemplo, a qué sección o elemento se refiere). El plan es implementar un parser inteligente de PDF con las siguientes características:

Detección de Jerarquía de Secciones: En vez de extraer texto plano “plano”, se interpretará el PDF como un árbol de secciones, subsecciones y párrafos. Herramientas como pdf.js-extract (ya incorporada) pueden obtener texto con posiciones, estilos, etc., lo que ayuda a identificar títulos y niveles por formateo (tamaños de fuente, negritas, indentación). Incluso existen APIs avanzadas (Adobe PDF Extract, etc.) que identifican hasta tres niveles de encabezados para capturar la estructura jerárquica del documento
developer.adobe.com
. Con esta jerarquía, cada sección del PDF (por ejemplo “1. Arquitectura”, luego “1.1 Muros”, “1.1.1 Resistencia al Fuego de Muros”) se puede reconocer y anidar correctamente.

Implementación: Aprovechar pdf.js-extract en modo “hierarchical” (ya iniciado en Fase 1) para obtener un JSON estructurado: por ejemplo un objeto/nodo por cada encabezado con sus textos hijos. Si pdf.js-extract no brinda todo lo necesario, complementarlo con análisis propio: detectar patrones como números/etiquetas de sección (1., 1.1, 1.1.1 etc.), cambios de estilo, o incluso procesar el índice si el PDF lo tiene.

Identificación de Reglas/Requerimientos: Una vez tenemos la estructura, necesitamos aislar las frases de requerimiento dentro del texto. Las reglas en la ET/normativa pueden aparecer como:

Listas enumeradas (bullets o numeración) con cada requerimiento explícito.

Texto narrativo donde las exigencias están descritas dentro de párrafos.

Tablas con especificaciones técnicas (p.ej., una tabla de cargas o dimensiones mínimas).

Para capturar esto:

Se detectarán listas y viñetas como elementos separados (ej. - La altura mínima de piso a cielo será 2.5m).

En texto corrido, buscar patrones indicativos de requisitos: verbos como "debe", "tendrá que", "se exigirá", o unidades numéricas (%, metros, grados, etc.). Por ejemplo: "los muros deben tener resistencia al fuego F-60" es claramente una regla (objeto = muros, propiedad = resistencia al fuego, valor = F60).

Tablas: representan un desafío, pero si la ET incluye tablas (ej. “Espesor mínimo de elementos estructurales”), el parser debería extraerlas. pdf.js-extract puede extraer texto posicional; tal vez se pueda reconstruir la tabla leyendo coordenadas. Alternativamente, si las tablas no son fácilmente parseables, este puede ser un punto a mejorar posteriormente o requerir input manual si crítico.

Propagación de Contexto (Etiquetado por Categoría): Cada regla extraída debe llevar consigo el contexto de dónde estaba en el documento. Esto permite saber a qué especialidad o elemento se refiere. Ejemplo:

Si una regla se encuentra bajo la sección "1.1.3 Columnas (Estructura)", se le puede asignar metadata: categoria = "Estructura" y quizá subtipo = "Columnas". Así sabemos que aplica a columnas estructurales.

Este etiquetado automático se basa en heredar los encabezados padres: en el ejemplo, el texto "Columnas" indica el tipo de elemento, y la sección ancestro podría ser "1.1 Estructura" o similar indicando la disciplina.

Con esto, solucionamos la ambigüedad: por ejemplo, la regla "Espesor mínimo: 20 cm" sola no dice de qué elemento, pero si está bajo "Muros", entenderemos que aplica a muros.

Almacenamiento de Reglas: Convertiremos las reglas en una estructura de datos manejable, por ejemplo:

{
  "id": "ET-1.1.3-a",
  "seccion": "1.1.3 Columnas",
  "categoria": "Estructura > Columnas",
  "descripcion": "Las columnas deben tener resistencia al fuego mínima F-60.",
  "parametro": "FireRating",
  "valor_requerido": "F60",
  "unidad": null,
  "fuente": "ET",
  "pagina_pdf": 34
}


Este es un ejemplo hipotético de cómo representar una regla. Notar que incluiríamos:

Una identificación (puede combinar la sección o un índice interno),

La descripción textual,

Quizá la abstracción de parámetro/propiedad y valor requerido (si logramos derivarlos, por ej. parametro = FireRating, valor = 60 minutos),

La categoría/especialidad,

La referencia a la fuente (ET o Normativa, y página del PDF).

Esta estructura permite luego comparar fácilmente con el modelo Revit (parametro vs valor) y dar mensajes claros.

Formato narrativo vs explícito: Si las reglas no vienen como lista clara sino incrustadas en texto largo, la extracción es más compleja. Habrá que apoyarse en técnicas de procesamiento de lenguaje o patrones:

Por ejemplo, buscar oraciones con números y unidades (p. ej. "espesor de 20cm", "separación no mayor a 5m", "grado de protección IP45").

Realizar cierta normalización de texto: remover simbolos innecesarios, unificar unidades (si la ET mezcla metros vs centímetros, etc., convertir a una unidad estándar).

En investigación sobre compliance automático se han usado enfoques de NLP avanzados (incluso entrenamiento de modelos) para extraer entidades y propiedades de textos normativos
nature.com
nature.com
. Por ejemplo, extraer entidades muro, columna y sus propiedades espesor, resistencia al fuego, altura, etc., a partir de texto no estructurado
nature.com
. Nuestro objetivo inicial puede lograrlo con reglas heurísticas simplificadas, pero conscientes de que es un problema complejo donde en el futuro podríamos incorporar NLP más sofisticado si hace falta. En resumen, si la ET está bien estructurada con listas de requisitos, nos apoyaremos en eso; si es muy narrativa, comenzaremos con expresiones regulares/búsquedas por palabras clave, sabiendo que habrá que iterar en mejorar esta extracción para alta precisión.

Detección Automática de Conflictos entre ET y Normativa

Si el sistema recibe tanto la Especificación Técnica (ET) del proyecto como una Normativa general, es posible que existan reglas solapadas o referentes a lo mismo. En algunos casos, la normativa puede exigir un estándar más estricto que el que pide la ET (por ejemplo, la ET dice resistencia al fuego F-60, pero la norma para edificios públicos exige F-120). Queremos que el motor detecte estas discrepancias automáticamente y decida qué criterio usar. El flujo para manejar esto:

Extracción por Separado: Primero, el parser obtendrá las reglas de la ET y las reglas de la Normativa independientemente, cada una con su estructura, contexto y valores.

Correspondencia de Temas: Por cada regla de la ET, el sistema buscará si hay alguna regla en la normativa sobre el mismo tema. Esto puede hacerse mediante:

Búsqueda de palabras clave relevantes en el texto normativo. Ejemplo: si la regla ET menciona "F-60" y "muros contra incendio", buscar en la normativa términos como "muros", "F-". Otro ejemplo: ET dice "baños accesibles según norma X", buscar en normativa "baños", "accesibilidad".

Indexar el contenido normativo (quizá usando una búsqueda vectorial simple o un índice invertido de términos) para encontrar rápidamente párrafos relacionados con la temática
nature.com
.

Dado que los documentos normativos pueden ser muy extensos (100+ páginas), podría no ser factible examinarlos enteros en cada análisis. Una optimización: pre-procesar la normativa al subirla, extrayendo sus secciones similares a la ET. Por ejemplo, si la ET tiene secciones de incendios, localizar en la normativa la sección de incendios.

Regla Activa (Supremacía): Si se encuentra una correspondencia, el sistema aplicará lógica de supremacía de la regla más estricta:

Caso A: Normativa más exigente – Si la normativa pide un nivel mayor que la ET (más seguridad), entonces se considerará esa como la regla obligatoria (Regla Activa). En el ejemplo de F-60 vs F-120, el requisito vigente será F-120 (el modelo deberá cumplir F-120). En las incidencias, se marcará que la ET pedía F-60 pero la norma exige F-120, por lo tanto se evaluó contra F-120. Esto se señala quizás como incumplimiento crítico, ya que involucra seguridad/código.

Caso B: ET más exigente o igual – Si la ET es igual o más estricta que la normativa, entonces la regla activa es la de la ET (no hace falta subir el estándar porque ya es >= normativa). En este caso, cualquier incumplimiento sería una desviación de lo especificado por el proyecto pero no necesariamente legal, así que podría considerarse de severidad menor (un warning de especificación).

Caso C: Requisito en Normativa no mencionado en ET – Puede ocurrir que la ET pase por alto algo requerido por norma. Si al analizar la normativa encontramos una regla aplicable que no tuvo equivalente en la ET, deberíamos agregarla como regla a chequear también. Es decir, aunque el proyecto no lo haya especificado, la herramienta igualmente verificará ese punto contra el modelo, para alertar de un posible incumplimiento legal no contemplado. Estos casos se reportarían también, quizás marcados como “Incumplimiento Normativa” exclusivamente.

Resolución de Conflictos: Para reglas coincidentes, podríamos almacenar en la estructura de regla un campo que indique origen dual (ET + Normativa) y el valor decidido. Por ejemplo, en el caso FireRating:

{
  "regla": "Resistencia al Fuego de Muros",
  "ET_requerido": "F-60",
  "Norma_requerido": "F-120",
  "Valor_aplicado": "F-120",
  "fuente_valor_aplicado": "Normativa"
}


Con esto sabemos que evaluaremos el modelo contra F-120. Esta información también sirve para presentar al usuario: podría mostrarse una nota en la incidencia indicando "La normativa exige un criterio más estricto que la ET; se aplicó F-120.".

Sin Normativa (Modo Solo ET): Si el usuario no proporciona un PDF de normativa, el sistema simplemente usa las reglas de la ET como única base de verificación. (En una etapa futura, se podría permitir configurar “normativas por defecto” si no suben ninguna, pero por ahora se asume input explícito).

Prioridades: En resumen, siempre se verifica primero el cumplimiento de la ET (primordial). La normativa se aplica como capa adicional: no para relajar nada, sino solo para elevar requisitos cuando sea necesario o añadir faltantes. Esto garantiza que el modelo cumpla tanto con lo especificado por proyecto como con estándares mínimos legales. En términos de severidad:

Incumplir la ET (proyecto) pero cumplir normativa -> Es un desvío de proyecto (posible warning a resolver con cliente).

Incumplir la Normativa (ley) -> Es un problema grave (error crítico) incluso si la ET no lo mencionó, porque implica riesgo de no aprobarse la construcción o comprometer seguridad.

Precisión y Tolerancias en la Verificación

Dado que se trata de requisitos técnicos de un edificio, la precisión de la detección debe ser muy alta. El sistema debe identificar todos los incumplimientos reales sin ignorarlos, ya que un falso negativo podría significar un riesgo de seguridad no detectado. Algunas consideraciones:

Detección Exacta vs Aproximada: Se intentará implementar las comparaciones de manera que sólo se apruebe aquello que cumple o supera la exigencia, sin aceptar valores inferiores. Por ejemplo, si se requiere resistencia al fuego 60 minutos, un elemento con 45 minutos debe marcarse incumplido; si se requiere altura mínima 2.50 m, un espacio de 2.45 m es incumplido.

Márgenes de Tolerancia: Idealmente, no debería haber tolerancia para parámetros categóricos o umbrales mínimos. No obstante, podrían haber escenarios donde la incertidumbre de datos deba considerarse:

Unidades o redondeo: si la ET pide 2.500 mm y el modelo tiene 2.499 mm, quizás es un tema de redondeo insignificante. Se podría definir una tolerancia mínima en porcentajes o unidades para evitar falsos positivos por diferencias de redondeo (ej. tolerar diferencias < 1% en longitudes). Pero esto debe usarse cautelosamente y de preferencia comunicarlo al usuario.

Campos textuales: por ejemplo, si un parámetro en Revit es texto ("Yes/No", "F-60" vs "F60"), asegurarse de normalizar formatos para compararlos correctamente.

Cobertura de Propiedades: La precisión también implica que estemos revisando todos los parámetros relevantes. Al inicio quizás enfocaremos ciertos tipos de requerimientos (dimensiones, resistencias, materiales, etc.). Habrá que mapear cada tipo de regla textual con el parámetro BIM correspondiente. Esto requerirá conocimiento del modelo Revit:

Ej: "resistencia al fuego F-60" corresponde al parámetro FireRating en muros/puertas con valor "60min" (o F60).

"Altura libre 2.5m" podría corresponder a la altura de una habitación o nivel – puede que en Revit no haya un parámetro único, sino se deba calcular diferencia entre nivel de piso y cielo falso, etc. Estas comprobaciones más complejas podrían requerir cálculos geométricos o de múltiples parámetros.

Recomendación: Comenzar con los parámetros que sí existen explícitamente en las propiedades (espesores de muros, altura de barandas, ancho de puertas, etc.). Para propiedades derivadas o implícitas (como alturas libres), tal vez se requiera obtener dimensiones geométricas del modelo (lo cual es más avanzado, pero APS/Forge permite acceder a geometría si es necesario, o el modelo puede exponerlo vía propiedades de habitaciones).

Validación Manual: Dado que la precisión debe ser alta, es importante probar el motor con algunos casos de ejemplo y, si es posible, validar manualmente algunos resultados. Cualquier incidencia marcada debe ser realmente un incumplimiento verificable en el modelo. Si el motor no está seguro de interpretar una regla, mejor no dar falso juicio automático; podría listarse como “posible incumplimiento a revisar” para un analista humano, en vez de afirmarlo erróneamente.

Actualización Continua: A medida que el motor se use en proyectos reales, se afinarán tanto la extracción de reglas como las comparaciones para minimizar errores. Cada nuevo tipo de regla identificada (por ejemplo, acústica, térmica, etc.) que quizás no estaba contemplada inicialmente, se incorporará al parser y al motor de comparación para ampliar la cobertura con precisión.

Integración con Visor 3D y Visualización de Incidencias

Uno de los aspectos más poderosos de esta herramienta será la visualización simultánea del modelo 3D con resaltado de elementos incumplidos y del documento PDF con los requisitos correspondientes. Para lograr esto:

Visor 3D (Autodesk Viewer via APS): Ya se cuenta con el visor de Autodesk Platform Services (antes Forge) integrado en la aplicación. Ahora se extiende su uso para resaltar elementos:

Utilizar la API del viewer (por ejemplo, viewer.highlight() o aplicando un Theming Color rojo) para marcar elementos específicos. Al conocer los IDs de elementos Revit (obtenidos del modelo traducido), se puede ordenar al viewer que los coloree o seleccione. Autodesk APS Viewer permite programáticamente seleccionar y hacer zoom a elementos no conformes de forma similar a como lo hace Model Checker dentro de Revit
interoperability.autodesk.com
.

Podría implementarse una extensión o simplemente usar las funciones de aislamiento: p.ej., viewer.isolate([elementId]) para aislar el elemento, o viewer.fitToView([elementId]) para encuadrarlo, y viewer.setThemingColor(elementId, new THREE.Color(1,0,0)) para colorearlo de rojo translúcido. De hecho, el concepto de “integración directa con el modelo” ya se destaca en herramientas de Autodesk donde uno puede “hacer zoom y seleccionar elementos no conformes directamente desde el reporte”
interoperability.autodesk.com
, que es justamente la experiencia que buscamos replicar en la web.

Navegación Libre: El visor seguirá permitiendo navegación libre (orbitar, paneo, etc.). Los usuarios pueden inspeccionar cualquier parte, pero en cuanto hagan clic en una incidencia, la cámara enfocará el elemento relevante. También se puede proporcionar botones para, por ejemplo, “Ver todos los elementos incumplidos” aislados a la vez, o navegar uno a uno.

Visor de Documento PDF: En la otra mitad de la pantalla, un componente visor de PDF (podría ser PDF.js en el frontend) mostrará la ET o la normativa:

Debemos ser capaces de resaltar texto en el PDF viewer. Una forma es conocer la página y coordenadas del texto del requisito. Con pdf.js-extract podemos obtener las coordinates bounding box de un párrafo en la página. Se puede transmitir eso al frontend para que el PDF viewer dibuje un highlight overlay. Alternativamente, más simple, si no queremos marcadores precisos, podemos simplemente desplazar (scroll) el PDF hasta la página y sección del texto relevante y quizás resaltar la línea en amarillo/rojo mediante el propio PDF.js textLayer.

Cada incidencia en la lista tendría asociada la referencia a la posición en el PDF (p.ej., página 34, sección 4.5.2). Al seleccionarla, el PDF viewer salta a esa ubicación y aplica un estilo destacado al texto. Así, el usuario ve exactamente qué dice la especificación que no se cumplió.

Panel de Incidencias: El panel lateral actúa como lista maestra de resultados:

Se mostrará una entrada por cada regla verificada, agrupada por cumplimiento o incumplimiento. Posiblemente, se puede separar en pestañas “Incumplimientos” y “Cumplimientos” o indicarlo con iconos (✅ para ok, ❌ para fail, ⚠️ para advertencia).

Cada incidencia mostrará un título breve (por ej. "Resistencia al fuego de Muros (F-120 requerido)") y un estado (Cumple/No cumple). Al expandir o hacer clic, puede mostrar detalles: qué valor exige la ET/norma vs qué valor tiene el elemento en el modelo, listado de elementos afectados (IDs o nombres).

Si múltiples elementos del modelo incumplen la misma regla, podría agruparse en la misma incidencia pero con conteo. Ej: "Muros con cortafuego F-120 – 3 elementos no cumplen (tienen F-60)". Al expandir, listar esos 3 elementos (quizá con sus identificadores o marcas únicas). Al seleccionar uno, el visor podría enfocarlo específicamente.

Incluir controles para filtrar esta lista por especialidad (si no se hizo antes) dinámicamente. Por ej., botones o checkboxes para ver solo Arquitectura, solo Estructura, etc., que oculten/muestren incidencias según su categoría etiquetada.

Codificación de Colores/Severidades: Se puede emplear colorimetría para prioridad:

Rojo para incumplimientos críticos (violaciones normativas de seguridad, por ejemplo).

Naranja/amarillo para incumplimientos de la ET (pero que aún cumplen la base normativa).

Verde para cumplimientos (si se decide listar también lo que está correcto, aunque podría enfocarse en mostrar solo lo que falla; quizás mostrar cumplimientos solo si el usuario lo solicita para verificar todo).

Estos colores reflejados tanto en los textos del panel, como en el highlight del modelo.

Interacción Bidireccional: No solo del panel hacia las vistas, sino idealmente también:

Si el usuario hace clic en un elemento del modelo 3D, podríamos destacar cuál regla(s) incumple ese elemento. Ej: selecciona un muro manualmente, el sistema revisa si ese muro está marcado en alguna incidencia y resalta en el panel la regla correspondiente.

Similarmente, si clickea en un texto del PDF (alguna regla), podríamos resaltar en el panel y en el modelo si hay chequeo para esa regla. Esto es opcional pero mejoraría la exploración manual.

Referencia cruzada: De esta manera, el entorno de revisión se vuelve muy intuitivo: el usuario ve simultáneamente la fuente del requerimiento y la manifestación en el modelo, pudiendo navegar por cada problema fácilmente.

Resultados, Manejo de Incidencias y Notificaciones

Tras el análisis, es necesario guardar y presentar los resultados de manera útil para el equipo:

Registro de Incidencias: Cada problema detectado se puede guardar en la base de datos como una entidad de Incidencia o Issue:

Atributos posibles: proyecto/modelo asociado, referencia a la regla (ID de regla extraída del PDF), descripción, severidad (critica/advertencia), estado (abierto, resuelto, etc. si se lleva seguimiento), timestamp, y posiblemente los elementos del modelo involucrados (sus IDs o GUIDs).

Esto permite que la información persista más allá de la sesión actual. Un arquitecto podría cerrar la app y al volver seguir viendo las incidencias pendientes. También serviría para historizar: por ejemplo, tras corregir el modelo y subir una nueva versión, se puede re-correr el análisis y comparar cuántas incidencias se resolvieron.

Notificaciones: La sugerencia de “barra con notificaciones de todos los modelos Revit que no cumplen...” implica que quizás haya una vista general (dashboard) donde se vea por proyecto un resumen:

Por ejemplo, Proyecto X – 5 incumplimientos (3 críticos, 2 advertencias). Proyecto Y – 0 incumplimientos (cumple todo).

Esto ayuda a priorizar dónde hay problemas. Cada entrada podría permitir entrar al detalle (abrir el visor y panel de ese proyecto).

Implementar notificaciones en la UI frontend que alerten al usuario (ej. un icono de campana con nuevos resultados) cuando termina un análisis, para que sepan que ya pueden revisar.

Reporte descargable: El usuario indicó que no es prioritario generar un PDF/Excel de informe descargable, prefiriendo gestionar incidencias dentro de la plataforma. En todo caso, tener los datos estructurados facilitaría si luego se quiere implementar un resumen exportable. Por ahora, el enfoque es interactivo dentro de la app en vez de generar documentos externos.

Distinción de Cumplimiento vs Inconsistencias: Debemos definir claramente categorías de resultado:

Cumple: El modelo satisface la regla dada. (Puede que no listemos todos estos para no abrumar, pero podrían estar disponibles).

No cumple: El modelo no alcanza el criterio de la regla (incumplimiento directo).

Inconsistencia: Podría interpretarse como cuando la ET y la Normativa difieren. Pero con la lógica de supremacía aplicada, quizás redefinimos inconsistencia como “la ET pide A pero la norma pide B, se tomó B”. Esto realmente se manifiesta como un incumplimiento de la ET (si A no se logra) y/o de la normativa. Quizá no necesitamos una categoría separada; en su lugar, clarificamos en la descripción de la incidencia si hay un conflicto de criterios.

Otra interpretación de "inconsistencia" podría ser si el modelo tiene datos contradictorios (por ejemplo dos parámetros relacionados que no cuadran). Sin embargo, eso ya escapa del ámbito de comparar con documentos.

Interfaz de Resultado: Como se describió, el panel de incidencias es el centro. Podría haber opciones de ordenar/sort (por severidad, por sección de la ET, etc.). También un campo de búsqueda para filtrar incidencias por palabra clave.

Estado de Incidencias: Si se desea un seguimiento, se podría permitir marcar una incidencia como "en revisión" o agregar comentarios. Pero esto ya se acerca a funcionalidad de issue tracking, que podría ser demasiado para primera versión. Inicialmente, con listarlas es suficiente; la gestión la harán externamente los usuarios.

Actualización de Modelo: Si se sube una nueva versión del modelo Revit, se tendría que re-ejecutar el análisis (quizás automáticamente) y actualizar las incidencias. Podríamos detectar cambios: por ejemplo, si un muro marcado como incumplido se corrigió, la siguiente corrida ya no lo listará. Esto podría marcarse como resuelto. Y si aparecieron nuevos incumplimientos, se agregan. Esto sugiere una funcionalidad futura de comparar resultados entre dos versiones.

Escalabilidad en Resultados: En proyectos grandes, puede haber decenas de incumplimientos inicialmente. La herramienta debe manejar bien esa cantidad: paginar la lista si son demasiados, agrupar similares como antes se mencionó, y permitir filtrado para enfocarse en lo importante.

Integración con la Arquitectura Tecnológica Existente

Finalmente, es clave implementar todo lo anterior aprovechando el stack actual de la “DOM BIM Platform” y herramientas disponibles, asegurando un desempeño aceptable:

Backend (Node.js + Express + TypeScript): Se creará un módulo o servicio nuevo, por ejemplo ComplianceCheckerService, que orqueste el análisis:

Procesamiento de PDF: Utilizar pdf.js-extract (preferido sobre pdf-parse debido a sus capacidades de mantener estructura jerárquica). Probablemente se tenga una función como parseDocument(pdfBuffer) que devuelve la lista estructurada de reglas (como objetos con secciones, textos, etc. según lo descrito).

Posiblemente, haya que hacer una Fase de entrenamiento/manual: si conocemos ciertos formatos de ET comunes, adaptar el parser a esos. Por ahora, hacerlo genérico con detección de encabezados y bullet points.

Para normativas, igual enfoque. Incluso se podría reutilizar la misma función y luego marcar las reglas con fuente "Normativa".

Análisis de modelo (APS): Gracias a Autodesk Platform Services, el modelo Revit una vez subido es traducido a un formato que nos permite consultar sus propiedades. Hay dos maneras principales:

Model Derivative API: Obtener un JSON de propiedades del modelo. Autodesk APS ofrece endpoint para obtener la estructura del modelo y sus properties. Se podría llamar una vez y guardar ese JSON (puede ser grande pero filtrable). Con Prisma/PostgreSQL, incluso podríamos almacenar los datos relevantes de propiedades en tablas para consultas rápidas (por ejemplo, una tabla de elementos con sus categorías y propiedades principales).

Viewer (frontend): Ya que el modelo se carga en el viewer, también se podrían extraer propiedades mediante llamadas desde el front (Viewer API tiene métodos como getPropertyDb()). Pero es mejor hacer las comprobaciones en el backend para robustez y para poder marcar incidencias server-side.

Una opción híbrida: usar el Model Derivative to get all properties, then perform queries in Node. For example, filter all elements of category X and get parameter Y values.

Comparador de Reglas vs Modelo: En el backend, implementar la lógica que recibe las reglas (con sus parámetros requeridos) y consulta el modelo:

Por cada regla relevante (o por cada combinación de regla y elemento del modelo):

Identificar los elementos del modelo a los que aplica. Por ejemplo, si la regla es de “Muros”, primero obtener la lista de todos los elementos de categoría Wall (muro) en el modelo, usando quizás la clasificación por categoría de Revit (que APS conserva en properties).

Luego verificar la propiedad específica: p.ej., cada muro -> leer su propiedad FireRating.

Comparar con el valor requerido (transformando unidades si corresponde).

Si no cumple, registrar la incidencia asociando esa regla con ese elemento. Si cumple, se puede omitir o marcar como tal.

Esto sugiere un bucle por categoría o por regla. Hay que ser cuidadoso con eficiencia: en modelos con miles de elementos, iterar por cada regla cada elemento podría ser lento. Mejor:

Iterar por reglas y dentro por elementos filtrados de esa categoría (más acotado).

O iterar por elements grouped by category and then check relevant rule(s) for that category.

Colas en segundo plano: Dado que este procesamiento puede tardar, integrarlo con BullMQ (Redis) para ejecutarse en un worker. Al pulsar "Analizar", el backend encola un job; el usuario puede ser notificado cuando termine (por WebSocket o consultando el estado).

Detección de conflictos ET vs Norma: También en backend, tras parsear ambos PDFs, implementar la comparación descrita (buscar reglas similares y determinar la activa). Esto idealmente se hace antes de checar el modelo, de modo que al checar ya sepamos el criterio final. Por ejemplo, al generar la lista de reglas a verificar, ya sustituir cualquier valor proveniente de normativa si es más estricto.

Base de Datos (PostgreSQL + Prisma): Diseñar modelos de datos para:

Documentos (ET, Normativa) asociados al proyecto (guardar quizás meta y path).

Reglas extraídas de cada documento (podemos guardarlas para depuración o reuso, aunque también se pueden regenerar cada vez; guardar podría ser útil si queremos mostrar al usuario la lista de requisitos o mantener historial).

Incidencias detectadas, con sus vínculos a reglas, elementos, proyecto, etc. Prisma facilitará definir estas relaciones.

Elementos BIM (podría almacenarse un subconjunto, pero quizá no necesario almacenar todos los elementos; con el JSON de propiedades en runtime puede bastar).

APIs: Crear endpoints para:

Iniciar análisis (POST /projects/:id/check-compliance).

Consultar estado del análisis (GET /projects/:id/check-compliance/status).

Obtener resultados (incidencias) (GET /projects/:id/issues).

Estos serán consumidos por el frontend (por ejemplo, para mostrar la lista de incidencias, o un websocket message when done).

Frontend (Next.js + React):

UI de carga: Ya existe para modelo y PDF, puede ajustarse para este flujo (asegurar validaciones, mostrar que la ET es obligatoria, etc.).

Página de resultados: Construir la vista con la división (Viewer 3D, PDF, Panel lateral). Utilizar Tailwind/ShadCN UI para el layout dividido.

Integrar un componente de PDF viewer (podría usar react-pdf o un wrapper de PDF.js).

El Autodesk Viewer ya está integrado; se puede reutilizar la instancia o crear una nueva en esa página.

Panel lateral: usar algún componente de lista/accordion de ShadCN UI para mostrar incidencias, con estilos personalizados para los estados.

Estado: Zustand o Context can manage state of current project’s issues, selected issue, etc., so that clicking an issue updates both viewer and PDF view.

Destacar en Viewer: Podría requerir una pequeña extensión de Forge Viewer en JS que reciba comandos para resaltar elementos. Por simplicidad, desde React podemos call viewerInstance methods if we have a reference. The selection/highlight can be done via the Forge Viewer API as described.

Destacar en PDF: Manipular el PDF viewer DOM to highlight text. Possibly simpler: use PDF.js text layer to find the text span. We might pre-store the exact text excerpt for each rule to help locate it via search in PDF.js.

Notificaciones: In the main layout of the app, we might add a notifications icon that shows completed analyses or new issues. This can subscribe to a WebSocket or periodically poll for analysis completion/ new issues.

Performance: Hay que considerar el rendimiento:

Parsing PDFs de cientos de páginas puede ser lento. Si pdf.js-extract es síncrono o lento, podría hacerse en un worker separado también. Quizá convenga generar los resultados de parse una sola vez y cachearlos (especialmente la normativa que no cambia frecuentemente).

Comprobar miles de elementos contra cientos de reglas = potencialmente muchas comparaciones. Optimizar filtrando por categoría como se dijo. También quizás implementando ciertas reglas globales con consultas agregadas (ej., “todas las puertas deben ser X” – en vez de iterar puertas una a una, uno puede preguntar a la DB si existe alguna puerta que no cumpla X, pero igual se termina iterando).

Usar Redis para colas, y posiblemente para caching de ciertos resultados si necesario.

Hacer ajustes según los resultados antes de mover a producción.
